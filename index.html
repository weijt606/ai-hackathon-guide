欧洲 AI 黑客松到底有哪些玩法？

查看本章原页 ↗

1. 不只是 Coding，什么都能 Hack

欧洲 AI 黑客松的玩法挺野的，跟 AI 时代之前的黑客松玩法不一样，远不止通宵写代码，一般有几种形式：

  • Hack Night：3–5 小时，通常围绕赞助商的 API 或指定技术栈快速构建一个 demo，然后全场路演。Hack Night 一般 solo 或者小团队友好，核心竞争力是对题目的理解和快速开发能力。新手可以先从 Hack Night 入坑，记得带上自己配置好的 Coding Agent，别把全部希望寄托在赞助商送的 API Credits 上。
  • Build Hackathon：经典玩法，一般 24–48 小时，有命题赛道也有完全开放选题，从想法到 MVP 到最后 live demo，这种大型比赛一般参赛队伍都比较多，通常会先进行 demo submission 或初轮评审，只有入围的团队才能登上 Final Stage。demo 提交后审核评分进入第二轮才有机会上台路演。想争取全场的 final stage 和兼顾 side track 还是挺难的。
  • Startup / GTM Hackathon：代码和构建 MVP 只是基础，重点在产品方向的市场调研，需要发布产品到生产环境，找用户、投广告、跑流量、签订 LOI，甚至拿到第一笔真实付费，这种比赛一般战线比较长，考察重点也是 GTM 的能力和结果，推荐构建能力没问题了、想实操 GTM，最好有社媒分发能力再尝试。
  • Themed Hackathon：围绕 AI Agent、Voice AI、Climate Tech 等具体方向，有时还会提供真实数据和 API。通常由科技公司、开发者社区或研究机构举办，有些会提供真实数据和 API。除了推广技术生态，也可能是为了寻找特定问题的解决方案或招聘员工。对某家公司或技术方向感兴趣的话，可以重点关注。
  • Invitation-only Hackathon：邀请制，通常面向有经验的 builder 或往届 winner。高手局，节奏也快，竞争激烈，非常刺激。

2. 奖项不止一个，甚至可以叠 Buff

很多欧洲 Hackathon 不是只有一个冠军。

  • Overall Winner：从进入 final stage 的队伍中评选，全场总排名，通常取 Top 3。
  • Side Track / Sponsor Challenge：赞助商单独出题，比如指定软件、模型、API 或技术栈，一个项目可以同时冲多个 challenge。
  • Wildcard：外卡晋级。有些比赛会在常规评审之外，给有潜力或表现特别的团队额外的 final stage 名额。
  • Final Stage：先经过 demo 提交评分之后的初选，再上台 live demo + pitch。3–5 分钟讲清楚几天的工作，主要做产品和结果展示，做 PPT 去讲的队伍已经很少了，直接打开产品 landing page 边讲边演示是主流玩法。
  • Overall Prize 和 Sponsor Challenge 可以同时拿，奖金和 credits 也能叠加。

3. 赞助商不只是发奖金

OpenAI、Anthropic、Google、Cursor、Lovable、n8n、Nebius、Entire、SLNG 等等，在我参加或关注的活动中，赞助方既有大型科技公司，也有初创团队；具体名单以各场赛事公布的信息为准。

奖励通常是现金 / API Credits / Cloud Credits / Mentorship 的几个形式的组合，见过最搞笑的奖励是和赞助商的 CEO 共进早餐 hhh。Overall Prize 和 Sponsor Challenge 都可能有现金奖励，具体取决于赞助商和主办方的安排。

02

欧洲 AI 黑客松去哪里找？

查看本章原页 ↗
本章目录 07 SECTIONS

1. Luma：我的主要信息源

这是我寻找欧洲 AI 活动时最常用的平台，Berlin、Paris、Barcelona、Amsterdam、London、Copenhagen 都有不少 AI Hackathon 和 Build Night。

先关注当地的 AI / Startup Community，再顺着 Organizer 找活动效率会很高。

Tips：关注 Organizer 比单纯搜索黑客松更有效。很多比赛需要申请审核，需要有开源项目 / 产品来投递，一般都要求添加 LinkedIn 链接，不是 RSVP 就能直接进。所以小白参赛前可以准备一下自己的 LinkedIn profile 和个人项目。

2. Devpost：传统黑客松大本营

老牌 Hackathon 平台，大型比赛、线上赛、企业 Challenge 非常多，适合全欧全球可飞的高手去赢奖金攒经验。

比赛规则、奖金池、Sponsor Challenge 通常写得很清楚，组织方一般都很正规很有经验，缺点是欧洲本地的小型 Hack Night 不一定会发布在 Devpost，而且不是基于城市信息检索，找本地信息比较费劲。

3. Meetup / Eventbrite：找本地 Builder

适合挖掘本地开发者活动，活动不一定叫 Hackathon，也可能是 AI Build Night/Day、Agent Jam、Vibe Coding Session 一类的。

刚入坑可以先参加这些小型活动，找队友组队，比直接冲大型比赛轻松不少，适合刷经验。

4. LinkedIn & X：跟着 Indie Hacker 找比赛

不少比赛是 Organizer / DevRel 或参赛者自己在社交媒体上发出来的，尤其是一些邀请制黑客松，可能根本没有公开报名入口。

5. 专业 Hackathon Organizer：直接关注主办方

除了活动平台，欧洲还有不少专门组织 Hackathon 的团队和社区，推荐关注这几个：

  • Tech:Europe：很活跃的欧洲 AI / Startup 社区，经常举办 AI Hackathon 和 Builder 活动。
  • Hackathon Hub：Hackathon 活动与开发者社区平台，可以关注 LinkedIn 欧洲各地的比赛信息。
  • Hackathons International：专注国际 Hackathon 和开发者活动。

6. Sponsorship：带着赞助去比赛

还有个挺实用的玩法：一些 AI 公司愿意提供 API Credits 或算力以及旅行经费，支持开发者带着它们的技术参加第三方黑客松。

可以直接联系 AI 公司，带上比赛链接、项目 idea 和预计 API 用量申请支持。

Tips：别只问能不能送 Credits / 支持差旅经费，带着具体项目去聊。

找到赛事信息，然后呢？评估比赛的价值

  • Organizer / Sponsors：组织方的专业程度和商业资源直接决定了比赛体验，一般有多年比赛历史的组织方更靠谱。
  • Format / Tracks：开放选题还是命题？Build 还是 GTM？想练习 build 的能力就多去以产品开发为导向的比赛，想提升 go to market 能力就去 Sales Hackathon。
  • Judging Criteria：评委方是什么背景，科技公司 / AI 赞助商背景的评委专业性一般都不差。
  • 奖金池：现金？Credits？还是其他资源？黑客松拿到的 credits 奖励支撑了很大一部分我个人开发的支出，尤其一些模型中转站类的公司非常大气。
  • Travel Support：有没有交通补贴或住宿支持。有差旅支持的黑客松一般门槛很高，很多都是邀请制。

最后一个经验：

先进入 AI Community，再找 Hackathon！很多好比赛好队友，都是在 community 活动认识的。

找到适合自己的比赛之后，接下来要考虑的是和谁一起参赛，以及如何组建一支配合顺畅的队伍。

03

欧洲黑客松参赛者画像 & 组队指南

查看本章原页 ↗
本章目录 05 SECTIONS
1. 欧洲 Hackathon 都是什么人在玩？2. Solo 还是组队？3. 去哪里找队友？4. 怎么判断队友靠不靠谱？5. 我的组队习惯

1. 欧洲 Hackathon 都是什么人在玩？

  • Students / Researchers：学生、博士、研究人员，尤其是 CS / AI / CV / NLP 相关专业大学生，技术基础扎实，精力旺盛，很多都是从大学黑客松开始入坑。
  • Software Engineers：大厂和 Startup 工程师，平时被 Jira 和 Sprint 追着跑，周末出来玩点自己喜欢的东西，一大部分抱着创立自己的 startup 的初心，也有很多是来找新的工作机会和社交的。
  • Indie Hackers / AI Builders：自带 Coding Agent 和成熟 Workflow，Ship 速度很快，大都是黑客松老手，有些人手里已经跑着好几个产品。
  • Founders / PMs / Designers：偏产品、UX 和 GTM，很多 Founder 直接带着创业 Idea 甚至成品项目来找技术合伙人或者 VC，这类参赛者 networking 能力很强，主要目的是接洽评委中的 VC 机构。
  • Serial Hackathoners：黑客松职业玩家，熟悉规则、评审重点和 Pitch。我接触的欧洲 AI 创客圈子联系挺紧密，经常在不同城市碰到熟人 hh。
  • 在校高中生：AI 创业圈和黑客松圈子的年轻化最近几个月感觉特别明显，最近一次参加的黑客松现场有 1/3 都是 20 岁以下甚至很多高中在校生。我的队友就有一个 17 岁的高中生，行动力执行力拉满不说，产品品味和市场嗅觉也非常不错，做 GTM 没有任何包袱和“羞耻心”，一个小时在瑞典的街头采访了 20 多位路人，真是震惊到我了。
  • 当然现场还有不少 DevRel、VC、Angel Investor，来找项目、挖人才或者只是单纯扩圈认识 Builder。

2. Solo 还是组队？

先说结论：大型活动大团队（3–4 人），小型 Hack Night 一类的几个小时的比赛 solo 完全 ok。

现在有了 AI Coding Agent 加持，很少见有人古法手搓产品了，所以有人会觉得我完全可以一个人干一个团队的活儿，but！经过我开局连续三场 solo 的经历，产品被认可，但是没有团队的加持，jury 要么怀疑你是否能一个人完成一个团队的活儿，要么觉得项目很难继续推进。后面在接触 VC 机构和加速器的时候有更明显的感觉，甚至有 VC 看上了我的项目但明确告诉我找好 cofounder 再聊下一步，这也让我更重视团队的长期合作能力。

说回组队，24–48 小时的比赛，我更喜欢 2–3 人的团队，沟通成本低，分工灵活出活儿快，当然团队中有一个话事人极为重要！在组队的初期就要定好出现争议的时候谁说了算，谁来拿最后的主意，不然大多数组队在开题阶段就聊崩了，我甚至见过因为在使用模型 / 技术栈上有分歧而散伙的。

团队成员通常需要覆盖几个角色：

Engineering / Product / Design / GTM / Pitch

一个人可以身兼数职。技术挑战复杂的话，再按需增加队友。但一定需要一个技术“大牛”，最好有架构师功底，能快速搭建架构，负责 git 和审计 pr。可别比赛都要开始了还有成员不知道怎么开 pr 怎么推代码。虽然有人可以只负责 marketing / pitch，但是有 AI 构建能力，推文档做 HTML 的 pitch deck，是 AI 黑客松的基础能力了。

最怕五个人组队，三个人开会，两个人写代码。

3. 去哪里找队友？

  • Discord / WhatsApp：主办方通常会提前建参赛群，有专门的 #team-formation 或 #looking-for-team 频道。发 Tech Stack、Idea，或者直接找缺人的队伍。
  • Idea Pitch / Team Formation：很多比赛 Kickoff 后会安排现场组队。30 秒上台路演自己的想法 / 项目，感兴趣的人现场加入。社牛的天堂。
  • Networking：现场或者大型黑客松前一天的 meetup 活动直接找人聊，交换想法和技术栈，聊得来就一起 Build。
  • LinkedIn / X：提前联系参赛者，尤其是活跃的 Builder 和往届选手。
  • AI community：其他 AI 活动中认识的 builder，找到合适的人可以邀请一起去参赛。

Tips：短赛尽量提前组队，磨合成本太高直接影响黑客松参赛体验。

4. 怎么判断队友靠不靠谱？

我现在组队基本不看 Title，更关注：

  • Execution：能不能独立开发，有没有个人作品，能否按时交付？
  • Ownership：有独立解决复杂问题的能力，起码会用 AI 工具来进行研判找解决方案。
  • Decision Making：性格果决爽快，能快速拍板，能求同存异不龟毛。
  • Scope Control：时间不够时敢砍功能，能抓住重点不要有一些奇奇怪怪的执念。
  • Tech Fit：技术栈、目标和工作节奏是否匹配，前面说的起码有熟练使用的 AI 工具和会用 git。

还有一点很重要：提前对齐目标！！！

有人想冲 Overall Winner 拿大奖，有人目标明确想拿 Sponsor Challenge，有人纯粹来试新 API 或者来社交。和队友目标一致，每次出现分歧的时候理一下参赛目标，很多问题就迎刃而解了。

5. 我的组队习惯

比赛开始前，先和队友花十几分钟对齐四件事：

  • Target：冲 Overall 还是 Side Track
  • Scope：最终 Demo 展示什么
  • Ownership：谁负责 Build、Design、GTM、Pitch
  • Deadline：什么时候和什么程度可以进行交付

Hackathon 时间太短，没必要搞复杂的项目管理，一个极其轻量化的 PRD 就够了，甚至一段话来做产品设计，别把比赛开成 Scrum Planning，除非一两周或者长期的赛制。传统开发模式开 ticket 的时间可能在黑客松现场都够直接完成快速交流 + 交付需求了。

总结就是 Good teammates >> Fancy tech stack.

团队目标和分工明确之后，就可以一起筛选题目，并根据比赛规则制定策略。

黑客松怎么选题？分享我的一些拿奖策略

1. 选题：先看规则，再想 Idea

拿到题目先别急着打开 Coding Agent 急头白脸一顿输出，先看清赛事规则。如果比赛有多个 Track，我会先筛选团队擅长、大家也感兴趣的方向。

然后把所有候选 Idea 摆出来，一起打分投票。

分享一个我们常用的 ICIP 评估法，从四个维度给每个 Idea 打 1–5 分：

  • Impact：解决的问题有多大？价值是否清晰？能否让评委产生共鸣？
  • Implementation：技术可行性如何？能否在规定时间内做出完整 Demo？
  • Creativity：想法够不够新颖？有没有让人眼前一亮的地方？
  • Pitch：能不能在几分钟内讲清楚？Demo 是否有足够的视觉冲击力？

汇总大家的评分，选出排名最高的 2–3 个 Idea，每人认领一个同时开始做一个不超过 30 分钟的快速验证（Quick PoC）。

验证核心 API 效果、技术风险和 Demo 路径，尽快确定最终方向。当然，有些主办方会直接给出 Judging Criteria 和评分权重。这种情况就按官方标准来，没必要自己重新发明一套。

Tips：选题阶段最怕无限 Brainstorming。给讨论设个 Deadline，时间到了就拍板。

2. 选题策略：先研究奖池

虽然这个策略有点功利，但是如果抱着能上台路演和能拿到名次的目的，除了 Overall Winner，很多比赛还有 Sponsor Challenge、Side Track 等奖项。

我通常会提前研究：

  • Tracks：哪些赛道适合我们的技术和经验，以及非常重要的：能否在两三分钟的 demo 和可能的 final pitch 中快速展示产品。
  • Sponsors：赞助方的 API 和模型或平台是否可以自然融入项目，同时快速了解他们的技术栈。

Tips：一个项目有时可以覆盖多个 Challenge，提高获奖机会，但别为了多拿一个 Sponsor Prize，硬塞完全用不上的 API 和软件。CI/CD pipeline 一类的工具可以多选，开发者基本都会用到。

3. Idea：Demo Value > Feature Count

我比较喜欢三个特点的 Idea：

  • 痛点具体：一句话就能让人理解为什么需要这个产品，且受众群体明确和可触达，一定要避免伪需求。
  • 交互简单：最好打开就能用，10 秒抓住注意力，60 秒体验核心价值。
  • 结果直观：输入什么，AI 驱动的部分（agent？），最后解决了什么，要一眼就能看懂，在 repo 或者 landing page 可以展示工作流。

恭喜你，如果具备上述这些特点和元素，你的黑客松之旅已经成功一半了。

现在大家都玩 Coding Agent 玩得飞起，Build 一个功能完整的 AI App 已经越来越容易，能拉开差距的是产品判断、品味和 Demo 的体验，当然非常重要的还有做 live demo 和 pitch 的能力。

选定方向只是开始。接下来，需要把这个想法压缩成两天甚至几个小时内能完成、能上线、能演示的产品。

Build & Launch：如何短时间 Ship 一个“好”产品？不要掉进许愿式编程漩涡

1. 先对齐产品，再开始 Build

AI Coding 时代，PRD 已经快成了被人人嫌弃的老古董。毕竟一句 Prompt 就能开工，但是许愿式编程在黑客松不太好使。

团队协作时我一定会先花 15–30 分钟和队友对齐几件事：

  • Product Vision：解决什么问题，目标用户是谁？
  • Core Features：MVP 必须有哪些功能，哪些直接砍掉？
  • Demo Flow：交互逻辑怎么设计，最值得展示的核心交互是什么？
  • Tech Architecture：用什么技术栈，前后端怎么分工，Agent / Workflow / API 怎么连接？
  • API Contract：模块之间如何通信？数据结构怎么定义？

不用写几十页 PRD，一页 Markdown / HTML，甚至一块白板就够了。当然可以打开你的 chatbot 录音模式，团队边聊边帮你们总结。

2. 带着自己的技术积累上场

黑客松现场的开发和 launch 速度，很大程度取决于平时的技术积累和产品 / GTM 经验，我通常会准备好一套经过验证的技术栈：

  • Coding Agent：调教好的 Claude Code、Codex，配好 Skills、Rules 和 Workflow。
  • AI Architecture：成熟的 Agent Orchestrator、LangGraph、Agent Workflow、RAG 和 Tool Calling 方案等等。
  • Boilerplate：熟悉的前后端框架、UI Components、Auth、Database。
  • Infrastructure：提前熟悉 CI/CD、Deployment。很多项目光在 Localhost 跑通还不够，尤其是互动类产品和 GTM Hackathon，需要真正部署上线，让用户和评委都能访问。对于没有复杂部署需求的项目，推荐直接用 Vercel + Supabase，或者 Lovable 这类工具快速上线。别把宝贵的 Build 时间浪费在折腾基础设施上。

Tips：我参加过的不少黑客松要求参赛产品在比赛期间开发，也有赛事允许使用开源框架、已有技术架构及配置好的 Coding Agent；是否允许以及如何披露，须按该场比赛规则确认。

当然，具体要看比赛规则，尤其是对预先开发代码的限制。但没必要在比赛现场重新研究一遍 Agent 架构，也没必要从零搭建一套 CI/CD。

3. Parallel Build，熟练 git，少开会

团队 Build 最怕短板效应导致的互相等待，两三个人的小团队，我一般会按模块拆分任务：

  • Frontend / UX：核心交互、主要产品页面、用户体验设计。
  • Backend / AI Agent / AI Engine：API、Agent Workflow、数据处理。
  • Integration / QA / Test：模块集成、测试、部署。（一般都是 Backend 顺手来做，除非人多项目复杂）
  • Product / GTM：Landing Page，做前期市调 + 收集用户反馈、准备 Pitch 页面（不推荐准备 PPT 一类的 Pitch Deck，一个精良设计的 Landing Page 是最好的展示素材）。

Tips 1：个人可以兼顾多个角色，关键是每个模块有人负责，而且有一个技术总负责人，来管理 git 仓库，来决策技术架构，这里推荐团队里技术最成熟的成员来做 code review，就算 pr 都是 claude / codex 在看，也需要把关和做决策的技术大牛。

Tips 2：提前约定 API Contract 和数据结构，各自开工，定时 Sync。最后才开始集成，很容易掉进 Integration Hell。

4. 时间管理：尽早部署，及时 Freeze

以 24 小时左右的比赛为例，我比较习惯这样的节奏：

  • 前 15%：技术验证 + 任务拆分 + 项目初始化。
  • 中间 55%：核心开发 + 集成 + 部署。
  • 后 15%：测试 + 修 Bug + 优化体验。
  • 最后 15%：Feature Freeze + 准备 Pitch + Live Demo。

比例可以根据比赛调整，核心是尽早跑通产品，我一般会尽早部署第一个保底版本，后面持续迭代。

5. Launch：别等产品完美，黑客松不可能作出完美产品！

常说产品开发的逻辑是先完成再完美，但一两天的黑客松不可能交付“完美”的产品。在瑞典的黑客松，我和团队不到八小时完成了 Build + Landing Page + Distribution 和用户验证。

产品发布到 Reddit 后不到一小时，就收到了来自圣保罗真实用户的正面评价，八个小时有 49 个 beta user 注册。但凡在某个环节追求完美，整个链条都会被拖慢。

6. Reliability：别让 Demo 死在最后一分钟

这一点我觉得特别重要。

产品 Launch 了，结果 Final Pitch 现场宕机，或者评委筛选时根本打不开链接，真的很尴尬。所以除了 Coding，最好还要有一些基本的产品工程经验：Testing、Validation、Deployment、Operations。

我的检查清单：

  • E2E Testing：完整走一遍真实用户路径。
  • Production Check：确认部署环境和本地行为一致。
  • Logs / Monitoring：开发过程中就要有意识地加入日志和监控，出问题时能快速定位、快速修复。别每次遇到 Bug 都让 AI 吭哧吭哧从头到尾翻一遍代码。黑客松最耗不起的就是 Debug 时间。
  • API Limits：检查 Credits、Rate Limits 和模型延迟。不止一次遇到上台 Pitch 的选手跑一半 token 没了，尤其赞助商提供的很有限的 token。
  • Cross-device：换台设备，用无痕模式测试。
  • Fallback：准备 demo 录屏，这个方法帮过我的大忙，大多数情况评委一般不会介意产品偶尔卡住的时候打开录制 demo 来继续演示。另外关键 AI 调用最好有降级方案，多添加几个模型或者 API。

API Key 过期、免费额度耗尽、数据库休眠，这些小问题足够毁掉一次黑客松体验。比赛中没人会在意“在我电脑上本来能跑的”这样的说辞。

7. 几个踩过的坑

  • Overengineering：架构设计得很漂亮，核心功能还没跑通。
  • Scope Creep：功能越加越多但没有核心没有重点。
  • Integration Hell：每个人的模块都能跑，一合起来就挂。
  • Localhost Syndrome：本地运行完美，部署后各种报错。
  • Last-minute Changes：Deadline 前改核心逻辑，直接把 Demo 搞崩。

每个坑我都踩过，希望我的经验能帮到大家少踩坑快出活儿。

产品上线之后，最后一步是把价值展示清楚：准备可靠的 Demo，并在有限的 Pitch 时间里让评委理解它。

06

Demo & Pitch：如何在几分钟内让评委喜欢上你的产品？

前面的章节讨论了选题、组队、开发和交付。本章进入黑客松的最后一关：Demo、Submission 和 Pitch。

我参加过的黑客松的 Final Pitch 只有 3 分钟，极个别 5 分钟或者 2 分钟。外加 2–3 分钟 Q&A。十几个小时甚至几天的开发和准备，最后必须浓缩成几分钟的展示。

1. Demo Video + Live Demo 准备：先跑通，再打磨，然后录制

其实从开始设计产品的时候就该想好最终怎么展示 Demo。我一般会提前设计好 Demo Flow，只展示最核心的路径：

  • Wow Moment：最好 Demo 的前 30 秒就能让评委眼前一亮。
  • Demo Data：提前准备测试账号 / 输入数据和使用场景，别现场登陆加载。
  • Live Demo：能现场操作就现场操作，提前检查网络、权限和设备。
  • Fallback：准备录屏和截图。一旦演示过程中产品宕机，瞬间切换准备好的素材。

Tips：尤其是 AI Agent 项目，模型可能需要十几秒才能返回结果。提前准备好中间状态、执行结果，或者想好等待时讲什么。我的小技巧就是可视化 Agent 工作流，等待时间快速点一下技术栈和工作流，避免让评委对着 Loading Spinner 看半分钟。

2. Submission：别在最后一步翻车

很多黑客松主办方会通过 Devpost 或主办方自己的平台甚至是 google form 提交作品。

常见的 Submission Materials：

  • Project Description：项目名称、解决的问题、核心功能。
  • Demo URL：可以直接访问的产品链接。
  • GitHub Repo：代码仓库，按要求开放访问权限，一些技术导向的比赛会要求 repo 中有 build_log.md 一类的文档。
  • Tech Stack：模型、API、框架和 Sponsor Integration。
  • Team & Tracks：团队成员个人信息、参赛赛道和 Sponsor Challenge。
  • Demo Video：通常 1–3 分钟，具体看比赛规则，按照前面设计的 Demo Flow 来录。

Tips：除非赛方要求纯录屏，否则强烈推荐摄像头 + 屏幕录制，边操作边讲解。真人出镜 + 现场演示的感觉，比录完屏再丢给 AI 包装成精美 Launch Video 有说服力得多。工具方面推荐 Loom / Tella，录制完不用下载上传油管，直接分享链接即可。

我的习惯是 demo 视频录制前就开始提前创建 Submission Draft，最后把 demo 视频链接加进去。另外，如果想冲击 Challenge 记得在开发过程中就要检查 Sponsor Challenge 的额外要求。有些需要单独勾选 Track，有些要求展示 API 的具体使用方式。到填表的时候发现还没弄就太晚了。

很多比赛会先通过 Submission 筛选 Finalist，评委会先看你的项目介绍、Demo Video 和 Live URL，再决定谁能进入 Final Stage。

3. Pitch：Talk is cheap. Show me your demo.

大部分 Final Pitch 只有 3 分钟，时间卡得很死。

准备充分的话，我通常会按这个结构：

Problem → Solution → Live Demo → Impact → Tech

但有个很实用的建议：

如果没来得及充分排练，或者对时间把控没那么自信，直接一上台就从演示 Demo 开始。先用一句话介绍产品，立刻打开 Demo，把最核心、最有冲击力的功能展示出来。剩下的时间再讲解决的痛点、技术亮点和 Impact。

毕竟讲到一半被主持人喊停，结果最重要的 Demo 还没展示实在太亏了，这个教训太惨痛了，有次拿全场第三名就是因为 Demo 只演示了一半，结束和评委聊起来，有人说我们要是能充分演示产品很有希望冲击全场第一，太可惜了。

推荐两套常用的 Pitch Flow：

  • 标准版：Problem → Solution → Demo → Impact → Tech
  • Demo First：One-liner → Live Demo → Problem → Impact → Tech

技术导向的比赛多留点时间讲 Architecture，GTM Hackathon 则重点展示用户反馈和增长数据。

时间不够就砍 Slides，别砍 Demo。

4. Pitch Deck / Slides：少一点，够用就行

很少有比赛会要求 PPT 了，我基本都是拿 Landing Page 或者一个 AI 生成的产品介绍 HTML 来讲，内容包括：

  • Problem / Solution：一两页讲清楚产品价值。
  • Demo：直接切到产品。
  • Impact / Traction：用户反馈、GTM 数据或关键指标。
  • Architecture：核心技术方案，尤其是 Sponsor Challenge。

三分钟的 Pitch，完全没必要准备十几页 PPT，素材尽量用真实产品截图、架构图和数据图表。

如果是复杂的 Agent Workflow，准备一张清晰的或者动态的 Architecture Diagram 效果很不错。

5. 表达：少说黑话，多打直球

欧洲 Hackathon 的评委背景很杂，工程师、Founder、VC、DevRel 都可能坐在台下。

几个我比较在意的细节：

  • 除了讲技术栈的时候都少堆术语。
  • 用具体场景：直接告诉评委用户遇到了什么问题，产品怎么解决。
  • 控制语速：尤其是英语 Pitch，紧张时很容易越讲越快，边演示边输出比较容易控制节奏。
  • 看评委：别全程盯着电脑或者提词器念（我从来没准备过提词器或者台词，表达全靠开发过程中构建的对产品和技术的理解），和评委 / 主持人 / 现场观众有眼神交流。
  • 排练：如果是团队一起来讲，至少完整和队友理过一遍流程，确认好分工和时间控制，确认 Demo 和切屏都顺畅。

还有个经验：尽量让一个人主讲，队友辅助。当然团队项目对所有人的情绪要考虑到，事先商量好就行，比如主讲人讲产品和 Demo 演示，队友分别讲市场痛点、技术架构或者负责 Q&A。

6. Q&A：提前模拟评委拷打

Final Pitch 后通常会有几分钟 Q&A，这个部分对评委判断参赛队伍的真实水平很重要。

我一般会和队友提前过一轮，重点准备这些问题：

  • Differentiation：市面上有没有类似产品？为什么需要你们？ChatBot / 大模型不能直接实现吗？
  • Technical Depth：AI 具体做了什么？在哪些环节起到了什么作用？为什么选择这个模型或架构？
  • Reliability：大模型幻觉、输出不稳定或者 API Cost 怎么控制处理？
  • Business / GTM：目标用户是谁？怎么获客？有没有真实用户？
  • Sponsor Integration：赞助商 API 用在了哪里？为什么需要它，是不是硬塞进去的？

Tips：回答时先给结论，再解释细节，不知道就直接说，没实现的功能也别硬吹。评委问的是技术或者市场问题，别回答成融资路演。

7. 其他经验

  • 正式演示前，再检查一遍浏览器权限、麦克风、摄像头，尤其最好提前测试笔记本电脑和大屏幕的连接，或者手机演示的话可能需要自备转换头。
  • 尤其是语音、视觉或者手势交互类项目，现场设备和环境变化很容易影响效果。
  • 还有一点：Pitch 前尽量 Feature Freeze，别再为了优化点小东西改代码导致产品演示出问题。
